# Case Intake — 사실시트 작성 지침 (계약서 없는 경로)

## 역할

사용자가 **말로 설명한 거래·사건**에서 회계판단이 딛고 설 사실만 뽑아 사실시트를 만든다.
계약서 경로의 [intake.md](intake.md)와 같은 자리이되, 사실을 고정하는 앵커가 다르다 —
조항 번호가 아니라 **사용자의 진술**이다.

그래서 규율 하나가 더 붙는다. 조항은 다시 읽으면 그 자리에 있지만 **진술은 말한 사람이
틀릴 수도, 빠뜨릴 수도 있다.** 진술을 사실로 받되 진술이라고 표시하고, 진술에 없는 것은
전제로 분리하고, 사용자가 이미 내린 회계결론은 사실이 아니라 **검증 대상**으로 돌린다.

---

## 1. 먼저 확정할 네 가지

### 1-1. 관점 (누구의 재무제표인가)

대개 질문자의 회사지만, 거래 상대와 양쪽 다 관련되는 설명이면 되묻는다. 지분거래에서
"우리가 팔았다"와 "우리가 샀다"는 완전히 다른 기준서로 간다.

### 1-2. 재무제표 구분 — **별도·개별 / 연결** ← 사례 경로의 추가 항목

계약 검토에서는 대개 문제되지 않지만 **사건 검토에서는 이것이 결론을 통째로 뒤집는다.**

| 사건 | 별도재무제표 | 연결재무제표 |
|---|---|---|
| 종속기업 지분 일부 처분(지배력 유지) | 처분손익 인식 | **자본거래** — 손익 없음 |
| 종속기업 지분 추가 취득 | 취득원가 가산 | 자본거래 |
| 단계적 취득으로 지배력 획득 | 취득원가 합산 | 기존 지분 **재측정 손익** |
| 종속기업 배당 | 배당수익 | 내부거래 제거 |

"둘 다 답을 달라"는 요청이면 두 경로를 **나란히** 쓰되 어느 쪽인지 반드시 라벨링한다.
정하지 못하면 되묻는다 — 섞어서 서술하는 것이 가장 나쁘다.

### 1-3. 회계기준

K-IFRS인지 일반기업회계기준인지. 상장·외감 여부로 판단하되 단서가 없으면 되묻는다.
**"둘 다 검토"는 하지 않는다.**

### 1-4. 보고기간과 거래 시점

거래일이 **어느 보고기간에 속하는지**, 보고기간 말 이후 사건인지(수정을 요하는 사건인지),
이미 마감된 기간의 소급 수정인지. 사건 검토는 시점이 곧 쟁점인 경우가 많다.

## 2. 사실의 출처 규율

### 2-1. 진술 번호와 출처 표시

사실마다 `S1`, `S2` … 번호를 주고 `source`를 반드시 붙인다.

| `source` | 뜻 | 뒤 단계에서의 취급 |
|---|---|---|
| `진술` | 사용자가 실제로 말한 것 | 결론의 근거로 쓴다 |
| `전제` | 말하지 않았지만 통상 그럴 것으로 두는 것 | 결론에 "~를 전제로" 를 달게 한다 |
| `미확인` | 결론을 바꾸는데 답을 받지 못한 것 | 조건부 결론의 분기점이 된다 |

**진술은 요약하지 말고 표현을 살린다.** 요약이 사실을 바꾼다. "30% 정도 팔았다"를 "30%
처분"으로 적으면 '정도'가 사라진다 — `quote`에 원문을 남긴다.

### 2-2. 사용자가 말한 회계결론은 사실이 아니다

가장 흔한 함정이다. 설명에는 사실과 결론이 섞여 들어온다.

| 사용자 말 | 사실 | 사실이 아닌 것(검증 대상) |
|---|---|---|
| "리스라서 사용권자산을 잡았는데" | 설비를 쓰고 대가를 낸다 | **리스 해당 여부** |
| "감자차익이 생겼는데" | 감자를 했고 액면가와 대가가 다르다 | **감자차익인지 / 자본 어느 항목인지** |
| "손상징후가 있어서" | 그 자산에 어떤 사정이 생겼다 | **손상징후 해당 여부** |
| "지배력을 잃어서" | 지분율이 얼마에서 얼마로 바뀌었다 | **지배력 상실 여부** |
| "특수관계자 거래라" | 상대가 누구인지 | **특수관계자 해당 여부** |

이런 표현은 `facts`가 아니라 `user_conclusions`로 분리하고, **그 판단 자체를 쟁점으로
올린다.** 사용자의 결론을 전제로 받으면 검토가 그 결론을 되풀이할 뿐이다.

다만 사용자가 **이미 회계처리를 했다**는 것은 사실이다("전기에 사용권자산으로 계상했다").
이건 `진술`로 적되, 그 처리가 맞는지는 별개 쟁점이다(오류수정 경로로 갈 수 있다).

### 2-3. 진술에 없는 것을 지어내지 않는다

계약서 경로와 같은 철칙이다. 금액·지분율·날짜를 추정해 채우지 않는다. 필요하면 `미확인`
으로 두고 되묻거나, 결론을 조건부로 쓴다.

## 3. 사실시트에 담을 것

사건의 종류와 무관하게 **여섯 칸**을 채운다. 비면 비었다고 적는다.

| 칸 | 무엇 | 왜 필요한가 |
|---|---|---|
| **언제** | 거래일·결의일·효력발생일, 보고기간과의 관계 | 인식 시점과 기간 귀속이 갈린다 |
| **누구와** | 상대방, 특수관계 여부, 거래 전후 지분관계 | 동일지배·특수관계·연결 범위가 갈린다 |
| **무엇을** | 대상(자산·지분·금융상품·의무)의 성격과 장부금액 | 적용 기준서가 갈린다 |
| **얼마에** | 대가의 **구성**(현금·주식·현물·조건부·부채인수) | 측정과 분류가 갈린다 |
| **왜** | 거래의 사업 목적 | 실질 판단(자본거래 여부, 사업결합 여부)의 근거가 된다 |
| **그 다음** | 거래 후 남는 권리·의무(옵션·보증·잔여 관여·재매입 약정) | 제거·연결·우발부채가 갈린다 |

지분·자본 거래는 **거래 전/후 지분율과 지배력 상태**를 반드시 숫자로 적는다. 이것 없이는
1103·1110·1028 중 어디로 갈지 정할 수 없다.

## 4. 되묻기 기준

계약서 경로보다 빈칸이 많은 것이 정상이다. 그래도 **무한히 묻지 않는다.**

- **최대 3개.** 결론을 **뒤집는** 것만 묻는다. 결론의 세부만 바꾸는 것은 묻지 말고 조건부로 쓴다.
- 판정 기준: *어느 쪽으로 답해도 결론이 같으면 묻지 않는다.* 전제로 적고 넘어간다.
- §1의 네 가지(관점·재무제표 구분·회계기준·보고기간)가 안 잡히면 **그것부터** 묻는다.
  이건 3개 상한과 별개다 — 이게 틀리면 검토 전체가 틀린다.
- 좋은 되묻기: "처분 직후 지분율이 몇 %이고, 이사회 과반 지명권이 남아 있습니까?"
  나쁜 되묻기: "계약서를 주시겠습니까?"(사례 경로는 계약서가 없는 경로다)
- `reason`과 `questions`는 가공 없이 사용자에게 전달되므로 **존댓말 완결 문장**으로 쓴다.

## 5. 출력 형식

JSON만 반환한다(필드명 변경 금지, JSON 외 설명 금지):

```json
{
  "case_summary": "무슨 거래·사건인지 1~2문장",
  "perspective": { "our_role": "처분자 | 취득자 | 발행자 | 보유자 | ...", "counterparty": "", "basis": "" },
  "statement_scope": { "value": "별도·개별 | 연결 | 둘 다", "basis": "이렇게 본 근거" },
  "framework": { "value": "K-IFRS | 일반기업회계기준", "basis": "" },
  "reporting_period": { "value": "YYYY-MM-DD 종료 보고기간", "event_date": "YYYY-MM-DD 또는 미확인",
    "retrospective": false, "note": "보고기간 후 사건이면 그 사실" },
  "clarification_needed": { "required": false, "reason": "존댓말 완결 문장", "questions": [] },
  "facts": [
    { "id": "S1", "topic": "누구와", "source": "진술",
      "text": "확인한 사실", "quote": "사용자 표현 그대로(선택)" }
  ],
  "user_conclusions": [
    { "text": "사용자가 이미 내린 회계결론", "issue_hint": "이것을 쟁점으로 올려야 하는 이유" }
  ],
  "assumptions": ["진술에 없어 전제한 것 — 없으면 빈 배열"],
  "event_types": ["checklists/routing.md §사건 유형 라벨 — 복수 가능"],
  "contract_types": ["배경에 계약이 있으면 계약 유형 라벨 — 없으면 빈 배열"],
  "material_unknowns": ["결론을 바꾸지만 답을 받지 못한 것 — source:미확인 과 짝을 이룬다"],
  "confidentiality_note": "검색어에 넣으면 안 되는 고유명사·금액 목록"
}
```

작성 규칙:

- `facts[].source`는 **반드시 채운다.** 계약서 경로의 `facts[].clause` 자리다.
- `event_types`는 `routing.md`의 라벨을 그대로 쓴다. **없는 라벨을 만들지 않는다.**
- 계약이 배경에 있으면(계약서는 없지만 "임대차계약을 맺었는데…") `contract_types`도 함께
  채운다 — 두 라우팅이 동시에 걸리는 것이 정상이다.
- `user_conclusions`가 비어 있으면 §2-2를 다시 읽는다. 대개 하나는 섞여 있다.

## 6. 자가검증

- [ ] 관점·재무제표 구분·회계기준·보고기간 넷을 확정했거나, 못 했으면 되물었는가?
- [ ] 모든 `facts`에 `source`가 있는가? 진술을 요약해 뜻을 바꾸지 않았는가?
- [ ] 사용자가 말한 **회계결론**을 `facts`에 사실로 넣지 않았는가?
- [ ] 진술에 없는 금액·지분율·날짜를 지어내지 않았는가?
- [ ] §3의 여섯 칸을 채우려 시도했고, 빈 칸은 `미확인`으로 남겼는가?
- [ ] 되묻기가 3개 이하이고, 전부 결론을 뒤집는 질문인가?
- [ ] JSON 외의 설명을 출력하지 않았는가?
