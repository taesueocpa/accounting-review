# Issue Mapping — 쟁점 도출 지침

## 역할

[0] 단계의 산출물을 받아 **실제로 판단이 갈리는 회계쟁점만** 골라내고, 각 쟁점에
**앵커 문단 키**와 보조 검색어를 붙인다. 근거를 수집하는 단계가 아니고 결론을 내는
단계도 아니다 — 다음 단계가 무엇을 읽어야 하는지 정하는 단계다.

**두 경로를 같은 방식으로 다룬다.** 계약서 경로는 팩트시트(`intake.md`)를, 사례 경로는
사실시트(`case-intake.md`)를 받는다. 다른 것은 사실의 출처뿐이다 — 전자는 `facts[].clause`
(조항 번호), 후자는 `facts[].source`(진술·전제·미확인). 쟁점을 만드는 규율은 동일하다.

핵심 둘: **사실에 걸리는 쟁점만 만든다**(체크리스트 항목을 전부 복사하지 않는다),
**앵커 키는 체크리스트에 적힌 것만 쓴다**(문단 번호를 기억으로 지어내지 않는다).

---

## 1. 절차

```
Step 1  contract_types / event_types → checklists/routing.md 로 모듈 세트 결정
        둘 다 있으면 두 세트의 합집합을 연다
Step 2  각 모듈 체크리스트를 Read
Step 3  체크리스트의 "계약에서 볼 곳" 과 facts 를 대조
        계약서 경로 → facts[].clause (조항이 있는가)
        사례 경로   → 그 열을 "확인할 사실" 로 읽고 facts[].text 와 대조
                      (체크리스트는 계약 문언으로 쓰여 있으나 묻는 것은 사실이다)
        → 걸리는 항목만 쟁점으로 승격, 안 걸리면 버린다
Step 4  사례 경로면 user_conclusions 를 훑어 §2-1 규칙대로 쟁점으로 승격
Step 5  쟁점마다 앵커 키(체크리스트에 적힌 것)와 보조 검색어를 붙인다
Step 6  쟁점 간 연결(한 판단이 다른 판단을 바꾸는 것)을 depends_on 으로 표시
```

- `contract_types`와 `event_types`가 둘 다 비었으면 routing.md의 "유형 불명" 절차를 따른다
  (경로에 맞는 쪽을 본다).
- 모듈 세트에 없더라도 팩트시트에 **명백한 트리거**가 있으면 해당 체크리스트를 추가로
  연다(예: 원상복구 조항 → 충당부채, 조건부 대가 → 사업결합).

## 2. 쟁점으로 승격하는 기준

**승격한다**: 그 사실이 실제로 확인되고(조항이 있거나 사용자가 진술했고), 그 해석에 따라
**인식·측정·분류·시기 중 하나가 달라질 때.**

### 2-1. 사용자가 내린 회계결론은 반드시 쟁점이 된다 (사례 경로)

`user_conclusions` 의 항목은 **그 판단 자체를 쟁점으로 올린다.** "리스라서 사용권자산을
잡았다"면 리스 해당 여부가, "감자차익이 생겼다"면 그 금액의 자본 내 분류가 쟁점이다.
사용자의 결론을 전제로 받으면 검토가 그 결론을 되풀이할 뿐이다.

예외는 **이미 한 회계처리**다. "전기에 사용권자산으로 계상했다"는 사실이므로 `facts` 에
남되, 그 처리의 적정성은 별도 쟁점이고 결론에 따라 `error-policy` 모듈이 추가로 열린다.

### 2-2. 승격하지 않는 것

- 체크리스트에 있지만 이 계약·거래에 해당 사실이 없는 항목
- 결론이 조항에서 자명하고 다툼의 여지가 없는 항목(팩트시트에만 남긴다)
- 금액적으로 명백히 사소한 항목(다만 "사소함"은 계약금액 대비로 판단하고, 판단 근거를 적는다)
- 계약 해석이 아니라 회사 내부 정책·시스템 문제(원가집계 체계 등) — `out_of_scope`로 분리

**쟁점을 부풀리지 않는다.** 모양 갖추기용 쟁점은 근거 예산을 잠식하고 검토의견서를
읽기 어렵게 만든다. 계약 하나에 쟁점 3~8개가 보통이고, 20개가 나오면 승격 기준을 다시 본다.

## 3. 앵커 키 규율

- 앵커 키는 **체크리스트 파일에 적힌 것만** 쓴다. 기억으로 문단 번호를 만들지 않는다.
- 키 형식은 `{기준서번호}-{문단번호}`이고 문단 번호는 숫자만이 아니다(`B34`, `IE325`,
  `6.1.1`, `한129.1`, `20A`). **받은 그대로** 넘긴다 — 정규화하면 조회에 실패한다.
- 일반기업회계기준은 장 번호가 기준서 번호 자리에 온다(`16-16.10`, `13-13.4`).
- 체크리스트에 앵커가 없는 쟁점, 그리고 routing.md의
  「체크리스트가 없는 영역」에 걸리는 쟁점(법인세·주당이익·공정가치 측정 등)은 `anchors`를
  비우고 `search_terms`만 채운 뒤 `anchor_gap: true`로 표시한다 — 다음 단계가 검색으로
  문단을 찾아야 한다는 신호다. **모듈이 없다는 이유로 쟁점을 버리지 않는다.**

## 4. 보조 검색어 작성

- **회계 용어로만** 만든다. 당사자명·금액·계약 고유명사를 넣지 않는다(`confidentiality_note` 참조).
- `standards`: 기준서 본문 검색용(앵커로 못 잡은 인접 문단을 찾을 때)
- `qnas`: 질의회신 검색용 — 사실관계 어휘를 넣되 일반화한다("전용 생산라인 최소보증물량" ○,
  "A사 평택공장 라인" ✗)
- `supervision`: myfss 검색용 — 감독당국이 쓰는 어휘로("수익인식 진행률", "우발부채 공시")

## 5. 출력 형식

JSON만 반환한다:

```json
{
  "path": "contract | case",
  "modules_opened": ["1115-revenue", "1037-provisions"],
  "modules_skipped": [{ "module": "1116-lease", "reason": "사용권 이전 조항 없음" }],
  "issues": [
    {
      "id": "issue-1",
      "title": "결론이 갈리는 쟁점을 한 줄로",
      "module": "1115-revenue",
      "priority": "high|mid|low",
      "why_it_matters": "이 판단에 따라 무엇이 달라지는지(인식 시점·금액·분류)",
      "fact_refs": ["F3", "F7"],
      "anchors": ["1115-35", "1115-B9"],
      "anchor_gap": false,
      "search_terms": { "standards": [], "qnas": [], "supervision": [] },
      "candidate_conclusions": [
        { "id": "A", "position": "기간에 걸쳐 이행", "trigger": "이 조항이면 이쪽" },
        { "id": "B", "position": "한 시점에 이행", "trigger": "저 조항이면 저쪽" }
      ],
      "depends_on": []
    }
  ],
  "cross_cutting": ["1008 회계정책 개발 필요", "IFRS 18 표시 영향"],
  "out_of_scope": ["계약 해석이 아닌 항목 — 사유와 함께"],
  "framework_note": "일반기업회계기준이면 어떤 장으로 갔는지"
}
```

작성 규칙:

- `fact_refs`는 `facts[].id`를 참조한다(계약서 경로 `F1`, 사례 경로 `S1`). **사실에 매이지
  않은 쟁점은 만들지 않는다.**
- `candidate_conclusions`는 **실제로 갈릴 때만** 만든다. 결론이 하나면 빈 배열로 두고
  `why_it_matters`에 방향을 적는다. 모양 갖추기용 반대 결론 금지.
- `depends_on`: 선행 판단이 있으면 그 issue id(예: 리스 식별이 부정되면 수익 쟁점으로 감).
- `modules_skipped`는 **반드시 채운다** — "판단해서 뺀 것"과 "안 봐서 없는 것"을 구별하는 칸이다.

## 6. 자가검증

- [ ] 모든 쟁점이 특정 사실(`F`/`S` 번호)에 매여 있는가?
- [ ] (사례 경로) `user_conclusions`를 전부 쟁점으로 올렸는가? 사용자의 결론을 전제로 받지 않았는가?
- [ ] 앵커 키를 체크리스트에서 가져왔는가? 기억으로 만든 번호가 없는가?
- [ ] 검색어에 계약 고유명사·금액이 섞이지 않았는가?
- [ ] 열지 않은 모듈의 사유를 적었는가?
- [ ] 쟁점 수가 계약 복잡도에 맞는가? (부풀리지도, 빠뜨리지도 않았는가)
- [ ] JSON 외의 설명을 출력하지 않았는가?
